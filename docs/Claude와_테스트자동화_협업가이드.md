# Claude와 테스트 자동화 협업 가이드

마지막 정리: 2026-10-20 (정기점검주기 AD230 테스트를 해 본 방식 기준)

## 1. 한눈에 보기

| 누가 | 하는 일 |
| --- | --- |
| **사용자** | 메뉴 테스트 요청, 업무 규칙·로직 문서 전달, 결과 중 "사양인지 오류인지" 확인, PR 병합 |
| **Claude** | 화면 탐색, 테스트 케이스 작성, 자동 테스트 코드 작성·실행, 결과 판정, 엑셀·PDF 작성, 진행 상황 보고 |

## 2. 진행 순서 (메뉴 하나 기준)

1. **요청**: 프로젝트 채팅에 "○○ 메뉴 테스트해줘"라고 쓴다. 메뉴마다 새 스레드 하나로 진행한다 (스레드가 길어지면 느려짐).
2. **자료 전달** (있으면): 그 메뉴의 업무 규칙, 로직 문서, 실제 사용 순서, 특별한 기능 설명. 말로 적어도 되고 파일을 올려도 된다.
3. **Claude 작업**: 회사 PC에서 화면을 직접 열어 보고 → 테스트 케이스를 회사 양식에 작성 → 자동 테스트를 만들어 실행 → 결과 판정.
4. **검토**: Claude가 오류·개선으로 본 항목을 사용자에게 설명한다. 사용자가 "이건 원래 그렇게 동작해(사양)" 또는 "오류 맞아"를 알려 준다.
5. **마무리**: 판정을 고친 최종 엑셀·PDF를 받고, 코드는 PR로 올라오면 사용자가 브라우저에서 병합한다.

## 3. 사용자가 준비해 주면 좋은 것

- **업무 규칙 / 기대 결과**: 예) "RBM은 시작일 다음날부터 누적하고, 누적이 주기값을 초과하는 날 계획 생성"
- **사양 확인**: Claude가 오류라고 본 것 중 원래 의도된 동작인지 알려 주기
- 녹화(codegen)는 필수가 아니다. 화면은 Claude가 직접 탐색한다.
- "하지 말 것" 목록이나 알려진 버그 목록은 따로 안 줘도 된다. Claude가 판단해서 결과에 적는다.

## 4. Claude가 하는 것

- **화면 탐색**: 회사 PC(D:\qa-auto)에서 원격으로 실행. 검색·목록·상세·하위목록·팝업(LOV)·새 창까지 확인.
- **테스트 케이스 작성**: 공통 케이스(조회·생성·수정·삭제·Excel 등) + 메뉴 고유 기능. 케이스마다 "조건 → 결과 → (오류면) 기대"로 짧게.
- **테스트 데이터**: 이름 앞에 `[sychoi]`, 모든 칸을 현실적인 값으로 채움, 사원 칸은 최신영. 다른 사람·원본 데이터는 절대 지우지 않음.
- **판정**: 업무 규칙과 달력 데이터로 **정확한 기대 날짜·값**을 계산해 비교. 오류는 날짜 표 등으로 쉽게 설명.
- **진행 보고**: 몇 분마다 짧게, 실제로 확인된 것만. 시각은 한국시간(KST).

## 5. 받는 산출물

| 산출물 | 내용 | AD230 예시 |

결과 표기: 엑셀은 **정상 / 오류**만 (정상은 QA내용 칸 비움), PDF는 **정상 / 오류 / 개선**. 못 한 항목은 "미수행"으로 이유와 언제 할 수 있는지 함께 적는다.

## 6. 한계와 주의

- **Claude(클라우드)는 QA 서버에 직접 못 들어간다** (회사 IP만 허용). 그래서 모든 실행은 회사 PC에서 한다.
- **회사 PC가 켜져 있고 Claude 데스크톱 앱이 실행 중이어야** 한다. PC가 꺼지면 작업이 멈췄다가 켜지면 이어진다.
- **오래 걸린다**: 데이터 생성·작업완료·삭제까지 하는 전체 실행은 몇 시간 (AD230 전체 약 3시간, 조회만 약 6분).
- 테스트 중에 결과 **엑셀 파일을 PC에서 열어 두면 저장이 막힌다**. 볼 때는 복사본으로.
- QA 서버 재배포 중(404)에는 기다렸다가 이어서 한다.
- 개선 항목은 회사 일정상 바로 안 고쳐질 수 있어 다음 차수에도 개선으로 남긴다.

## 7. 다음 메뉴부터 달라지는 점

- AD230에서 만든 **공통 부품**(모든 칸 채우기, 저장, LOV, 그리드)과 **엑셀·PDF 생성 스크립트**를 그대로 재사용하므로 다음 메뉴는 더 빨라진다.
- 공통 케이스는 고정, 메뉴별 부분은 화면에서 자동으로 채우고, 사용자는 **특별 기능의 업무 규칙만** 알려 주면 된다.
